# Pantry Relay build contract

Owner: Shivam Gupta. Product: approved pantry-network surplus rebalancing to fill next-service category gaps. No household personal data. No AI API dependency. All sample organizations fictitious; demo is explicitly labeled.

Stack: React + TypeScript + Vite frontend, FastAPI Python backend, SQLite WAL transactional persistent single-instance pilot deployment. Backend serves frontend/dist; dev proxy /api to 8010. App runs at http://localhost:8010 after build.

## API contract (backend agent owns implementation, communicate changes)
All API response JSON except exports. Errors {detail: string}. UTC ISO timestamps; lb floats max 2 decimals; categories produce, protein, dairy, grains, pantry. Storage ambient, chilled, frozen.

Auth: POST /api/auth/register {name,email,password,network_name} -> {user,csrf_token}; POST /api/auth/login {email,password}; POST /api/auth/demo {} creates isolated demo network with data, user and csrf_token; GET /api/auth/me -> {user,csrf_token}; POST /api/auth/logout. Cookie HttpOnly session; authenticated mutating endpoints require X-CSRF-Token. user {id,name,email,role,network_id}; roles admin, coordinator, driver. Registration creates admin with empty workspace. Rate limit sensitive endpoints. Demo configurable enabled. Credentials never stored plaintext. POST /api/invites {role:coordinator|driver} -> {token,expires_at}; POST /api/auth/join {token,name,email,password} -> auth response. GET /api/team -> {users,invites}. Admin only invites. Registration/join minimum password 12 chars.

GET /api/workspace -> {user,network:{id,name,is_demo},sites:Site[],lots:Lot[],needs:Need[],transfers:Transfer[],events:Event[],metrics:{received_lb,active_transfers,available_lb,at_risk_lb,unmet_need_lb}}
Site {id,name,city,address,lat,lng,storage_types:string[],capacity_lb,notes,created_at}. Capacity means maximum stock held across all storage. Current lots plus inbound reservation must fit total capacity. POST /api/sites fields same excluding id,created_at. PATCH /api/sites/{id}. Physical location coordinates entered by coordinator, no geocoding API. Sites are network tenant scoped.
Lot {id,site_id,food_name,category,storage,quantity_lb,reserve_lb,available_lb,expires_at,restricted:boolean,notes,version,created_at}. quantity = physically held stock; reserve = protected minimum; available excludes protected minimum and all outbound reserved/accepted transfers. Expiry is operational use-by cutoff entered by pantry; no safety certification. Restricted lots cannot transfer. POST /api/lots fields excluding computed/id/version/created_at. PATCH /api/lots/{id} with version mandatory to reject stale adjustments. Audit inventory updates. No negative or non-finite quantities. Lots can't leave source under reserve. Physical stock decreases at pickup. Once received destination lot is added preserving provenance and expiry, and needs filled count increases.
Need {id,site_id,category,quantity_lb,fulfilled_lb,reserved_lb,remaining_lb,service_at,notes,created_at}. quantity is total requested. remaining excludes fulfilled and incoming reserved,accepted,in_transit,arrived. POST /api/needs {site_id,category,quantity_lb,service_at,notes}.
POST /api/planner {max_distance_miles:50,vehicle_capacity_lb:500,refrigerated:true} -> {proposals:Proposal[],excluded:[{lot_id,reason}],generated_at,assumptions:string[]}. Proposal {lot_id,need_id,source_id,destination_id,food_name,category,storage,quantity_lb,distance_miles,score,reasons:string[],expires_at,service_at}. Deterministic explainable FEFO greedy proposal allocation globally prevents double allocating stock/needs/capacity within batch. Haversine distances clearly approximate straight-line, no route claim. Respect max distance, vehicle capacity per transfer, cold capability, quantity reserve, need due date, unexpired food, restricted lots, destination storage and capacity. Prioritize service urgency and expiry; deadline must fit soonest use. No proposal for same source/dest. Return no feasible transfer gracefully.
POST /api/transfers {lot_id,need_id,quantity_lb,max_distance_miles,vehicle_capacity_lb,refrigerated} -> Transfer. Atomic recompute feasibility. Repeated duplicate should conflict if resources exhausted. POST /api/transfers/{id}/accept {receiver_name}; POST .../pickup {temperature_f:number|null,condition_confirmed:true}; POST .../arrive {}; POST .../receive {received_lb,temperature_f:number|null,receiver_name,exception_reason:string}; POST .../cancel {reason}. State reserved -> accepted -> in_transit -> arrived -> received; cancelled permitted only reserved/accepted. No replay; conflict on invalid transition. Required cold temp logs at pickup and receipt; out of configured bounds block and instruct policy exception (no override). Chilled 32-41F, frozen <=0F. Food safety checks assist operator; no claim of certified safe food. expired pickup/receipt rejected. Actual received <= dispatched, rejected remainder recorded with mandatory exception reason. Received stock increases destination; actual receipt reduces need, rejected remainder reopens demand. Hold inbound capacity until receipt. Driver can pickup and arrive only, cannot inventory/planner/create/accept/receive/cancel. Admin/coordinator full operations except invites admin only. Transfer {id,lot_id,need_id,source_id,destination_id,food_name,category,storage,quantity_lb,received_lb,status,distance_miles,receiver_name,exception_reason,created_at,updated_at,pickup_temperature_f,receipt_temperature_f}. Audit events each mutation. Status colors front: reserved amber, accepted blue, in_transit blue, arrived purple, received green, cancelled gray.
GET /api/reports/receipts.csv -> tenant scoped actual receipts and exception lb. GET /api/reports/audit.csv -> tenant scoped audit. Escape spreadsheet formula injection. No claimed meals/CO2/people served. GET /api/health -> minimal health. Production rejects unsafe config, no demo data in real registration. Seed demo relative timestamps on creation so showcase works anytime.

## Design direction
Warm ivory background, deep forest green primary, vivid leaf/lime accents, ink text, editorial serif display + clean sans body. Desktop persistent sidebar; compact responsive mobile nav. Distinctive central Iowa schematic network map using original SVG based on demo coordinates with label 'Schematic · straight-line distances'. No external maps dependency. High contrast, keyboard operability, actual form labels, live validation, visible loading, empty and error states, no dead buttons. Icons via lucide-react. Display demo data label persistently. Landing + login/signup/join; accessible product within a unified app.

Tabs: Overview (metrics, top opportunity, map, shortage list, recent activity), Relay planner (constraints + ranked proposals with explainability + reserve actions), Inventory (search, lots, add lot modal and protected reserves), Pantries (sites + add form + needs form), Deliveries (state progression + action modals + printable manifest), Impact (actual receipts, exception quantities, CSV export), Team (invite link and members). Every view uses real backend data. A role driver sees Deliveries only. API utility stores CSRF in memory and fetch credentials include; auth/me on initial load. No invented hidden data or simulated latency.

## Demo story
Fictitious Cedar Grove Pantry has produce surplus but protected stock for its own visitors. Fictitious Eastside Community Pantry needs produce for tomorrow. Planner explains a 120-lb transfer, rejects a restricted lot and incompatibility. Coordinator reserves/accepts, records pickup, arrives, and confirms 112 lb received with 8 lb damaged. Dashboard counts 112 actual lb, opens remaining need, preserves audit trail. Exact seed quantity can vary but keep first proposal intuitive. Demo dry run can use full 120 lb to shorten.

## Reviewed release refinements

- Local port is8010; Docker internal port remains8000.
- `GET /api/config` exposes demo/registration mode. Public demo-only hosting disables real registration and invitations. All disposable demo networks prohibit invitations.
- Need has `closed`; `POST /api/needs/{id}/close {reason}` closes an obsolete request if it has no active transfers.
- Transfer can end in `failed`; `POST /api/transfers/{id}/fail {reason}` closes an in-transit/arrived incident without returning source stock or pretending the food arrived. `failed_lb` records the loss.
- Transfer serialization includes `service_at`, `late`, `on_time` and `need_credited_lb`. Confirmation after the requested service does not credit that service, even when safely accepted food counts as throughput.
- Received stock gets a full protected reserve by default. Restricted and expired lots expose zero shareable availability.
- Full rejection with accepted weight0 and a reason may record missing/out-of-policy temperature or an expired lot, without creating stock or falsely recording accepted food.
- Schema migrations through version3 preserve earlier inventory and transfer history.
